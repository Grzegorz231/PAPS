**Тема:** Проектирование REST API для ИИ-ассистента техподдержки

## 1. Проектные решения

1. Протокол: Использование HTTP/1.1 с передачей данных в формате JSON.
2. Архитектурный стиль: REST. Ресурсы четко разделены на понятия онтологии и пользовательские тикеты.
3. Обработка ошибок: Стандартизированы коды ответов. Например, если ID запроса не найден при попытке уточнения, сервер возвращает 404, а если данные некорректны - 422.
4. Версионность: Реализован префикс `/v1/` в URL - задел на будущее, чтобы ничего не поломалось.
5. Модели данных: Для всех входных и выходных данных созданы Pydantic-схемы.
6. Методы: 
   * GET для безопасного чтения базы знаний;
   * POST для тяжелых операций (анализ текста через LLM/онтологию);
   * PUT/DELETE для управления жизненным циклом заявки.
7. Именование: Использование camelCase для ключей в JSON и kebab-case для URL-путей.
8. Stateless: Сервер не хранит сессию пользователя. Вся информация для обработки передается в теле запроса.

---

## 2. Спецификация API

### Методы GET
* `GET /v1/ontology/terms` — Список всех понятий из Protege.
* `GET /v1/ontology/terms/{id}` — Детальная информация об одном понятии.

### Методы POST
* `POST /v1/enrichment/analyze` — Основная логика: отправка жалобы на анализ ИИ.
* `POST /v1/tickets` — Создание финального технического отчета.

### Методы PUT и DELETE
* `PUT /v1/enrichment/refine/{id}` — Добавление уточнений к запросу.
* `DELETE /v1/enrichment/cancel/{id}` — Удаление черновика запроса.
